## 🛠️ Что и как проверено

1. **Фронтенд (UI/UX):** Проведено сплошное функциональное тестирование формы, проверены граничные значения и классы эквивалентности для всех полей ввода на фоне валидного окружения.
2. **Безопасность (Security):** Выполнена проверка текстовых полей на устойчивость к хранимым XSS-атакам и SQL-инъекциям.
3. **Интеграционный слой (REST API):** Написана автоматизированная коллекция Postman со встроенными JavaScript-автотестами для проверки структуры JSON-ответов сервера.
4. **Бонусная автоматизация (E2E):** Написан моностек автотестов на **Pytest + Playwright** (`bonus/tests/`).
5. **Бонусный SQL запрос:** Сам придумал задание и сам выгрузил таблицу (`bonus/`)

## 🚨 Почему этот релиз НЕЛЬЗЯ катить в прод (Отчёт о тестировании)

По результатам тестирования продукт получил статус **REJECTED**. Фича полностью не готова к релизу по следующим критическим причинам:

* **Полное отсутствие серверной валидации:** Бэкенд тотально игнорирует бизнес-логику и пропускает в базу данных любой невалидный мусор (даты в прошлом, короткие телефоны, 13 гостей при лимите в 12). Если фронтенд упадет или запрос отправят напрямую по API, БД будет мгновенно загрязнена битыми контактами.
* **Уязвимость к инъекциям:** Фронтенд не фильтрует спецсимволы на уровне ввода, беспрепятственно пропуская SQL-конструкции и вредоносные скрипты на экран успеха.
* **Нестабильность сервера (500 ошибки):** При банальном отсутствии обязательного поля `name` бэкенд падает в `500 Internal Server Error` вместо цивилизованного ответа `400 Bad Request` из-за отсутствия глобального обработчика исключений валидации.
* **Бизнес-логика времени сломана:** Система позволяет бронировать столик «задним числом» на прошедшее время текущего дня (например, выбрать слот 12:00, когда на часах 15:45), что приведет к финансовым и репутационным потерям ресторана.
