## 1. Введение и Цель тестирования

### 1.1 Описание фичи

Функционал онлайн-бронирования столика представляет собой клиент-серверное приложение, состоящее из:

- **Фронтенд** — React/Next.js, реализует форму бронирования с клиентской валидацией полей ввода, отображением состояний (лоадер, экран успеха) и интеграцией с REST API.
- **Бэкенд** — Python/FastAPI, предоставляет REST API-эндпоинт `POST /api/booking` для приёма, валидации и обработки запросов на бронирование.

Пользователь заполняет форму (имя, телефон, дата, время, количество гостей), после чего данные отправляются на сервер. Сервер валидирует данные, проверяет доступность столиков и возвращает результат бронирования.

### 1.2 Цель тестирования

- **Верификация бизнес-логики** корректности работы сквозного флоу бронирования: от заполнения формы до получения подтверждения.
- **Валидация полей ввода** на UI-уровне (клиентская валидация при blur и при отправке) и на бэкенд-уровне (валидация входящих данных).
- **Проверка интеграции** через REST API-эндпоинт `/api/booking` — корректность кодов ответов, структуры тела запроса и ответа.
- **Оценка готовности** фичи к релизу на основе критериев начала/приостановки/завершения тестирования.

## 2. Объект тестирования (Scope)

### 2.1 In Scope (в область тестирования входит)

| Компонент                        | Описание                                                                                     |
|----------------------------------|---------------------------------------------------------------------------------------------|
| Форма бронирования на UI         | Поля: имя гостя, номер телефона, дата, время (слоты), количество гостей (1–12).            |
| Логика валидации на UI           | Валидация при потере фокуса (blur) и при отправке формы (submit). Отображение ошибок.       |
| Экраны состояний                 | Лоадер на кнопке «Забронировать» в момент отправки запроса; экран успешного подтверждения; кнопка «Забронировать ещё». |
| REST API `/api/booking` (POST)   | Обработка валидных и невалидных запросов; коды ответов 200/201 (успех) и 400 (ошибка валидации). |
| Бэкенд-валидация                 | Проверка корректности входных данных на стороне сервера, независимо от клиентской валидации. |

### 2.2 Out of Scope (в область тестирования НЕ входит)

| Компонент                        | Причина исключения                                         |
|----------------------------------|-------------------------------------------------------------|
| Нагрузочное тестирование         | Не входит в текущий спринт/релиз.                          |
| Тестирование производительности  | Время отклика, время рендеринга формы.                     |
| Орфография и тексты UI           | Не относится к бизнес-логике.                              |
| Дизайн-реквью (UX/UI)            | Не относится к бизнес-логике, если элементы функциональны. |
| Тестирование email/SMS-уведомлений | Если реализованы отдельно, вынесены в следующий спринт. |
| Тестирование админ-панели        | Не входит в функционал бронирования для клиента.            |

## 3. Критерии валидации данных

Ниже приведены правила валидации для каждого поля формы. Тестирование должно подтвердить, что данные правила применяются как на UI, так и на бэкенде.

### 3.1 Имя гостя

| Параметр          | Значение                                                          |
|-------------------|-------------------------------------------------------------------|
| Минимальная длина | 2 символа                                                         |
| Допустимые символы | Буквы (кириллица, латиница), пробелы, дефисы                    |
| Недопустимые символы | Цифры, спецсимволы (!@#$%^&*...), эмодзи                       |
| Примеры валидных  | `Иван`, `Мария-Анна`, `John Doe`, `Александр-Пётр`               |
| Примеры невалидных | `А` (слишком короткое), `Иван1`, `Петр@`, `` (пустое)          |

| Допустимые разделители | Пробелы, скобки `()`, дефисы `-`                                      |
| Количество цифр   | Ровно 10 цифр после кода страны (без учёта разделителей)                 |
| Примеры валидных  | `+7 999 123-45-67`, `8 (999) 123-45-67`, `+79991234567`, `89991234567`  |

## 4. Стратегия и Подходы к тестированию (Test Techniques)

### 4.1 Применяемые техники тест-дизайна

#### 4.1.1 Классы эквивалентности (ECP — Equivalence Class Partitioning)

Для каждого поля ввода данные разбиваются на классы эквивалентности:

| Поле          | Валидный класс              | Невалидные классы                        |
|---------------|-----------------------------|------------------------------------------|
| Имя           | 2+ букв, пробелов, дефисов  | 1 символ, цифры, спецсимволы, пустое     |
| Телефон       | +7/8 + 10 цифр + разделители | Неправильный код, <10/>10 цифр, буквы    |
| Дата          | 31.08.2026 – 29.11.2026     | До минимальной, после максимальной        |
| Время         | 12:00–22:00 с шагом 1 час   | За пределами диапазона, дробное          |
| Гости         | 1–12                        | 0, 13+, отрицательные, дробные, текст    |

Каждый класс эквивалентности проверяется одним тестовым случаем (представительным значением).

#### 4.1.2 Граничные значения (BVA — Boundary Value Analysis)

| Поле          | Нижняя граница | Выше нижней | Норма | Ниже верхней | Верхняя граница |
|---------------|:--------------:|:-----------:|:-----:|:-------------:|:---------------:|
| Имя           | 2 символа      | 3 символа   | 5     | 50            | 51              |
| Телефон       | +7 999 11-11-11 | валидный   | —     | валидный      | +7 999 999-99-99 |
| Дата          | 31.08.2026     | 01.09.2026  | —     | 28.11.2026    | 29.11.2026      |
| Дата (до)     | 30.08.2026 (-1) | —          | —     | —             | —               |
| Дата (после)  | —              | —           | —     | —             | 30.11.2026 (+1) |
| Время         | 12:00          | 13:00       | —     | 21:00         | 22:00           |
| Время (до)    | 11:59          | —           | —     | —             | —               |
| Время (после) | —              | —           | —     | —             | 22:01           |
| Гости         | 1              | 2           | 6     | 11            | 12              |
| Гости (до)    | 0              | —           | —     | —             | —               |
| Гости (после) | —              | —           | —     | —             | 13              |

#### 4.1.3 Попарное тестирование (Pairwise)

Для комбинаций параметров, влияющих на доступность столиков, применяется попарное тестирование (метод Ishikawa / pairwise):

| Параметр    | Значения                                  |
|-------------|-------------------------------------------|
| Дата        | Пн–Пт (будни), Сб–Вс (выходные)           |
| Время       | 12:00–15:00 (обед), 18:00–20:00 (ужин), 21:00 (поздний) |
| Гости       | 1–2 (малая), 3–6 (средняя), 7–12 (большая) |

Ключевые попарные комбинации:

| Дата        | Время  | Гости | Сценарий                                      |
|-------------|--------|-------|-----------------------------------------------|
| Будний день | 12:00  | 1–2   | Легко забронировать                           |
| Будний день | 19:00  | 4     | Пиковое время, середина                     |
| Выходной    | 19:00  | 8–12  | Максимальная загрузка, большой стол           |
| Выходной    | 22:00  | 12    | Крайний слот, максимальная вместимость       |
| Будний день | 12:00  | 12    | Крайний слот по гостям, будний день           |

### 4.2 Виды тестирования

| Вид тестирования         | Описание                                                                                          |
|--------------------------|--------------------------------------------------------------------------------------------------|
| Функциональное          | Проверка корректности работы каждого поля формы и бизнес-логики бронирования.                    |
| Позитивное              | Тестирование валидных сценариев: пользователь заполняет форму корректными данными и получает подтверждение. |
| Негативное              | Тестирование невалидных данных: некорректные значения в полях, отправка пустых форм, обход клиентской валидации через API. |
| Регрессионное           | Повторная проверка уже работающих сценариев после внесения исправлений или новых коммитов.        |
| API-тестирование         | Тестирование эндпоинта `POST /api/booking` через Postman/Insomnia: проверка кодов ответов (200/201, 400), структуры JSON, валидации на бэкенде. |
| Приёмочное (UAT)        | Финальная проверка сквозного флоу бизнес-пользователем (Product Owner / менеджер ресторана).     |
| Кросс-браузерное        | Проверка работы формы в Google Chrome и Mozilla Firefox (актуальные версии на август 2026).      |

## 6. Критерии начала, приостановки и завершения тестирования

### 6.1 Критерии начала тестирования

Тестирование может быть начато при выполнении следующих условий:

1. **Доступность демо-стенда** — фронтенд-приложение развёрнуто и доступно по URL, форма бронирования открыта и отрисована.
2. **Доступность API** — эндпоинт `POST /api/booking` отвечает на демо-стенде (HTTP 200/500 в зависимости от корректности запроса).
3. **Готовность коллекции Postman** — коллекция с запросами к `/api/booking` создана и проверена.
4. **Готовность тестовых данных** — набор тестовых данных (валидные и невалидные значения) сформирован и утверждён.
5. **Code Review пройден** — код фичи прошёл ревью и мержнут в ветку `staging` / `qa`.

### 6.2 Критерии приостановки тестирования

Тестирование приостанавливается при обнаружении следующих блокирующих проблем:

1. **Сквозной флоу не работает** — пользователь не может завершить бронирование ни при одном наборе валидных данных (формальное падение на любом шаге: отправка, валидация, подтверждение).
2. **Падение бэкенда с HTTP 500** — сервер возвращает `500 Internal Server Error` на валидный POST-запрос к `/api/booking`.
3. **Неработоспособность валидации на бэкенде** — сервер принимает невалидные данные (например, гости = 100, дата = 01.01.2020) без возврата `400 Bad Request`.
4. **Критическая регрессия** — изменение в коде сломало ранее работавший функционал, не имеющий workaround.

Тестирование возобновляется после исправления блокирующих дефектов и повторного развёртывания на демо-стенде.

### 6.3 Критерии завершения тестирования

Тестирование считается завершённым при выполнении всех следующих условий:

1. **Выполнены все запланированные тест-кейсы** — 100% тест-кейсов из тест-сьюта исполнены (покрытие по полям, граничным значениям, попарным комбинациям, API).
2. **Локализация дефектов** — все обнаруженные дефекты задокументированы, классифицированы по Severity / Priority. Ожидаемое количество дефектов: **3–8** (включая баги разной степени серьёзности).
3. **Отсутствие Critical / Blocker** — отсутствуют неисправленные дефекты с Severity = `Critical` или `Blocker`. Допускается наличие дефектов с Severity = `Major` / `Minor` при наличии согласованного workaround и решении Product Owner о выпуске.
4. **Утверждение тестирования** — тестирование утверждено Product Owner / Tech Lead / Project Manager.
5. **Отчёт о тестировании** — сформирован итоговый отчёт с результатами тестирования, статистикой дефектов, рекомендациями по выпуску.
