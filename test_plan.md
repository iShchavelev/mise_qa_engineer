## 1. Введение и Цель тестирования

### 1.1 Описание фичи

Функционал онлайн-бронирования столика представляет собой клиент-серверное приложение, состоящее из:

- **Фронтенд** — React/Next.js, реализует форму бронирования с клиентской валидацией полей ввода, отображением состояний (лоадер, экран успеха) и интеграцией с REST API.
- **Бэкенд** — Python/FastAPI, предоставляет REST API-эндпоинт для приёма, валидации и обработки запросов на бронирование.

Пользователь заполняет форму (имя, телефон, дата, время, количество гостей), после чего данные отправляются на сервер. Сервер валидирует данные, проверяет доступность столиков и возвращает результат бронирования.

### 1.2 Цель тестирования

- **Верификация бизнес-логики** корректности работы сквозного флоу бронирования: от заполнения формы до получения подтверждения.
- **Валидация полей ввода** на UI-уровне (клиентская валидация при blur и при отправке) и на бэкенд-уровне (валидация входящих данных).
- **Проверка интеграции** через REST API-эндпоинт — корректность кодов ответов, структуры тела запроса и ответа.
- **Оценка готовности** фичи к релизу на основе критериев начала/приостановки/завершения тестирования.

## 2. Объект тестирования

### 2.1 In Scope (в область тестирования входит)

| Компонент                        | Описание                                                                                     |
|----------------------------------|---------------------------------------------------------------------------------------------|
| Форма бронирования на UI         | Поля: имя гостя, номер телефона, дата, время (слоты), количество гостей (1–12).            |
| Логика валидации на UI           | Валидация при потере фокуса (blur) и при отправке формы (submit). Отображение ошибок.       |
| Экраны состояний                 | Лоадер на кнопке «Забронировать» в момент отправки запроса; экран успешного подтверждения; кнопка «Забронировать ещё». |
| REST API (POST)   | Обработка валидных и невалидных запросов; коды ответов 200/201 (успех) и 400 (ошибка валидации). |
| Бэкенд-валидация                 | Проверка корректности входных данных на стороне сервера, независимо от клиентской валидации. |

### 2.2 Out of Scope (в область тестирования НЕ входит)

| Компонент                        | Причина исключения                                         |
|----------------------------------|-------------------------------------------------------------|
| Нагрузочное тестирование         | Не входит в текущий спринт/релиз.                          |
| Тестирование производительности  | Время отклика, время рендеринга формы.                     |
| Орфография и тексты UI           | Не относится к бизнес-логике.                              |
| Дизайн-реквью (UX/UI)            | Не относится к бизнес-логике, если элементы функциональны. |
| Тестирование email/SMS-уведомлений | Если реализованы отдельно, вынесены в следующий спринт. |
| Тестирование админ-панели        | Не входит в функционал бронирования для клиента.            |

## 3. Критерии валидации данных

Ниже приведены правила валидации для каждого поля формы. Тестирование должно подтвердить, что данные правила применяются как на UI, так и на бэкенде.

### 3.1 Имя гостя

| Параметр          | Значение                                                          |
|-------------------|-------------------------------------------------------------------|
| Минимальная длина | 2 символа                                                         |
| Допустимые символы | Буквы (кириллица, латиница), пробелы, дефисы                    |
| Недопустимые символы | Цифры, спецсимволы (!@#$%^&*...), эмодзи                       |
| Примеры валидных  | `Иван`, `Мария-Анна`, `John Doe`, `Александр-Пётр`               |
| Примеры невалидных | `А` (слишком короткое), `Иван1`, `Петр@`, `` (пустое)          |

### 3.2 Номер телефона

| Параметр          | Значение                                                                 |
|-------------------|--------------------------------------------------------------------------|
| Формат            | РФ формат: код `+7` или `8`, далее 10 цифр                               |
| Допустимые разделители | Пробелы, скобки `()`, дефисы `-`                                      |
| Количество цифр   | Ровно 10 цифр после кода страны (без учёта разделителей)                 |
| Примеры валидных  | `+7 999 123-45-67`, `8 (999) 123-45-67`, `+79991234567`, `89991234567`  |
| Примеры невалидных | `+7 999 123-45-6` (9 цифр), `9 999 123-45-67` (неверный код), `+799912345678` (11 цифр), `abc` |

### 3.3 Дата

| Параметр          | Значение                                                                 |
|-------------------|--------------------------------------------------------------------------|
| Минимальная дата  | 31 августа 2026 г. (текущая дата, точка отсчёта)                         |
| Максимальная дата | 29 ноября 2026 г. (+90 дней от текущей даты, включительно)               |
| Недопустимые даты | Даты до 31.08.2026, после 29.11.2026    |

### 3.4 Время (слоты)

| Параметр          | Значение                                                                 |
|-------------------|--------------------------------------------------------------------------|
| Диапазон          | С 12:00 до 22:00 (последний слот — 22:00)                                |
| Шаг               | 1 час                                                                     |

### 3.5 Количество гостей

| Параметр          | Значение                                                                 |
|-------------------|--------------------------------------------------------------------------|
| Диапазон          | Строго от 1 до 12 (включительно)                                         |
| Тип данных        | Целое число                                                              |
| Недопустимые      | `0`, `13`, `-1`, `5.5`, `abc`, пустое значение                           |

## 4. Критерии начала, приостановки и завершения тестирования

### 4.1 Критерии начала тестирования

Тестирование может быть начато при выполнении следующих условий:

1. **Доступность демо-стенда** — фронтенд-приложение развёрнуто и доступно по URL, форма бронирования открыта и отрисована.
2. **Доступность API** — эндпоинт отвечает на демо-стенде (HTTP 200/500 в зависимости от корректности запроса).
3. **Готовность коллекции Postman** — коллекция с запросами к создана и проверена.
4. **Готовность тестовых данных** — набор тестовых данных (валидные и невалидные значения) сформирован и утверждён.

### 4.2 Критерии приостановки тестирования

Тестирование приостанавливается при обнаружении следующих блокирующих проблем:

1. **Сквозной флоу не работает** — пользователь не может завершить бронирование ни при одном наборе валидных данных (формальное падение на любом шаге: отправка, валидация, подтверждение).
2. **Падение бэкенда с HTTP 500** — сервер возвращает `500 Internal Server Error` на валидный POST-запрос.
3. **Неработоспособность валидации на бэкенде** — сервер принимает невалидные данные (например, гости = 13, дата = 01.01.2026) без возврата `400 Bad Request`.

Тестирование возобновляется после исправления блокирующих дефектов и повторного развёртывания на демо-стенде.

### 4.3 Критерии завершения тестирования

Тестирование считается завершённым при выполнении всех следующих условий:

1. **Выполнены все запланированные тест-кейсы** — 100% тест-кейсов из тест-сьюта исполнены.
2. **Локализация дефектов** — все обнаруженные дефекты задокументированы, классифицированы по Severity / Priority. Ожидаемое количество дефектов: **3–8** (включая баги разной степени серьёзности).
3. **Отсутствие Critical / Blocker** — отсутствуют неисправленные дефекты с Severity = `Critical` или `Blocker`. Допускается наличие дефектов с Severity = `Major` / `Minor` при наличии согласованного и решении Product Owner о выпуске.
4. **Утверждение тестирования** — тестирование утверждено Product Owner / Tech Lead / Project Manager.
5. **Отчёт о тестировании** — сформирован итоговый отчёт с результатами тестирования, статистикой дефектов, рекомендациями по выпуску.
